# Knock fit for Cadence: in-app notifications

Date: 2026-11-11

Scope: how Knock fits Cadence, a React Router framework-mode app with SSR on Node, React 19.2, a cookie session that holds a numeric `userId`, and in-app notifications only. Every claim below links a primary source: Knock docs, the knocklabs GitHub repos, the npm registry, or the Novu and MagicBell docs and pricing pages. ## Answer in brief

1. **Triggering.** `@knocklabs/node` v1.x is generated by Stainless (1.0.0 shipped 2025-05-01, after 0.6.19). The call is `await knock.workflows.trigger(key, { recipients, actor?, data?, tenant?, cancellation_key?, settings? }, { idempotencyKey?, timeout?, maxRetries? })`, and it returns `{ workflow_run_id }`. Runs execute asynchronously. Recipients can be identified inline as `{ id, name, ... }`. Defaults are a **60 s timeout and 2 retries**, so we must lower them and catch errors. That keeps a slow Knock from blocking the action. `Idempotency-Key` works on trigger only and is cached for 24 h.
2. **Feed and badge.** Mount `KnockProvider`, then `KnockFeedProvider`, then `NotificationIconButton` and `NotificationFeedPopover`, and import `@knocklabs/react/dist/index.css`. The badge counts **unseen** by default (`badgeCountType="unread"` switches it). The popover calls `markAllAsSeen()` when it opens. Real-time updates come over a WebSocket using the `phoenix` client. React 19 is a supported peer. **SSR caveat** *(source)*: `KnockProvider` creates the Knock client and runs inline `identify` *during render*, which means on the server too. Gate it with `enabled={hydrated}`.
3. **Identity.** IDs are strings: use `String(user.id)`. The v1 call is `users.update(id, props)`; v0 had `users.identify`. Enhanced security mode requires an RS256 JWT, signed server-side with `signUserToken(String(id))`, which defaults to a 1 h expiry. Pass it to `KnockProvider userToken=` and refresh it via `onUserTokenExpiring`. The secret key stays server-only. The public key and feed channel ID go to the browser. Each environment has its own keys and data.
4. **Preferences.** A preference set holds `workflows`, `categories`, `channel_types` (including `in_app_feed`), `channels`, and `conditions`. Precedence is environment default, then tenant default, then user. Users *can* opt out of `in_app_feed` per workflow. For mandatory notices, a workflow can "Override recipient preferences". **`@knocklabs/react` ships no prebuilt preferences UI.** It has a `usePreferences` hook, and the docs show a build-your-own `PreferenceCenter`.
5. **Pricing.** The Free plan includes **10,000 messages per month**, unlimited environments, preferences, and built-in multi-tenancy. Per-tenant preferences and branding are Enterprise-only. **Each in-app feed item counts as a message.** Usage accrues in every environment, and the in-app channel has no sandbox mode. Neither the pricing page nor the plans page lists enhanced security as a gated feature.
6. **Alternatives.** Nothing makes Knock the wrong choice. Novu and MagicBell both ship a prebuilt preferences UI, which Knock doesn't. Novu's free tier caps you at 5 workflows. MagicBell's free tier is 1,000 deliveries per month.
7. **Risks.** Server-side identify and timer leaks during SSR. Integer IDs colliding when several developers share one Knock dev environment. No official mock or offline mode. Dev usage is billable. The default 60 s timeout. The prebuilt popover's own CSS (`rnf-*`) clashing with Tailwind styling.

## 1. Triggering workflows from route actions (`@knocklabs/node`)

**Install and construct.** Install with `npm install @knocklabs/node`. Construct with `new Knock({ apiKey })`. The `apiKey` falls back to the `KNOCK_API_KEY` environment variable. Other options are `timeout`, `maxRetries`, `logLevel`, `logger`, `fetch`, and `fetchOptions` ([knock-node README](https://github.com/knocklabs/knock-node)). `baseURL` defaults to `KNOCK_BASE_URL`, then `https://api.knock.app` (*source*: [`src/client.ts`](https://github.com/knocklabs/knock-node/blob/main/src/client.ts)). The SDK requires Node 20 LTS or later and TypeScript 4.9 or later ([README](https://github.com/knocklabs/knock-node)).

**How v0 and v1 differ.** v0.6.x used `new Knock("sk_...")`, `knock.users.identify(id, props)`, `knock.users.getPreferences(id)`, and the static `Knock.signUserToken(id, opts)` ([v0.6.19 README](https://raw.githubusercontent.com/knocklabs/knock-node/v0.6.19/README.md)). v1.x is generated by Stainless. It uses an options-object constructor, `users.update` (an upsert, i.e. identify), `users.getPreferences(id, setId)`, and `users.setPreferences(id, setId, body)`. `signUserToken` became a named export, "explicitly exported to follow pre-stainless implementation" (*source*: [`src/index.ts`](https://github.com/knocklabs/knock-node/blob/main/src/index.ts), [`src/resources/users/users.ts`](https://github.com/knocklabs/knock-node/blob/main/src/resources/users/users.ts)). The 1.0.0 changelog has no migration guide. `MIGRATION.md` returns 404 ([CHANGELOG](https://github.com/knocklabs/knock-node/blob/main/CHANGELOG.md)). Treat older blog snippets that call `users.identify` as stale.

**Trigger signature in v1.41.1** (*source*: [`src/resources/workflows.ts`](https://github.com/knocklabs/knock-node/blob/main/src/resources/workflows.ts)):

```ts
trigger(key: string, body: WorkflowTriggerParams, options?: RequestOptions): APIPromise<{ workflow_run_id: string }>

interface WorkflowTriggerParams {
  recipients: Array<string | InlineUser | InlineObject>; // max 1,000
  actor?: string | InlineUser | InlineObject | null;
  cancellation_key?: string | null;   // needed for later workflows.cancel
  data?: Record<string, unknown> | null; // 10MB payload limit
  settings?: { sandbox_mode?: boolean; skip_delay?: boolean } | null;
  tenant?: string | InlineTenant | null;
}
```

The REST endpoint is `POST /v1/workflows/{key}/trigger`. It returns `200 {"workflow_run_id": "..."}`, and "All workflow runs are executed asynchronously." It sits in **rate-limit tier 5** ([API ref: trigger](https://docs.knock.app/api-reference/workflows/trigger)). So a successful trigger only tells us Knock accepted the run. Delivery happens afterwards.

**Inline identification.** Recipients, `actor`, and `tenant` can be upserted inline. Each recipient must then be an object with `id` (`{ "recipients": [{ "id": "user-123" }] }`) ([Identifying recipients](https://docs.knock.app/managing-recipients/identifying-recipients)). This lets Cadence skip separate identify calls: send `{ id, name, avatar }` with each trigger.

**Idempotency.** The `Idempotency-Key` header is honoured **only on** `POST /workflows/:key/trigger`. Keys can be up to 255 characters and are retained for 24 h. Only 2xx responses are cached. A replay returns the original response with `idempotent-replayed: true`. Reusing a key with different parameters returns an error ([Idempotent requests](https://docs.knock.app/api-reference/overview/idempotent-requests)). The SDK sends `Idempotency-Key: stainless-node-retry-<uuid>` on every non-GET call, and the key stays the same across its own retries. You can override it with the per-request option `{ idempotencyKey }` (*source*: [`src/client.ts`](https://github.com/knocklabs/knock-node/blob/main/src/client.ts), [`src/internal/request-options.ts`](https://github.com/knocklabs/knock-node/blob/main/src/internal/request-options.ts)). Use a domain key, for example `lesson-published:${lessonId}`, so a user re-submitting a form doesn't send the notification twice.

**Rate limits.** The rate-limits page lists 1, 5, 60, 200, and 1,000 requests/s rows, but the tier labels are missing from the page text. So I can't confirm from the page which rate tier 5 maps to. Limits are scoped per environment key, or per environment plus user when a user token is used. A rate-limited request gets `429` ([Rate limits](https://docs.knock.app/api-reference/overview/rate-limits)). The docs don't mention a `Retry-After` header.

**Errors, timeouts, retries.** Every error extends `APIError`: `BadRequestError` 400, `AuthenticationError` 401, `RateLimitError` 429, `InternalServerError` 5xx, `APIConnectionError`, and `APIConnectionTimeoutError`. The SDK retries 2 times by default with exponential backoff on connection errors, 408, 409, 429, and 5xx. The default timeout is **1 minute**, configurable via `timeout` and `maxRetries`, both globally and per request ([README](https://github.com/knocklabs/knock-node)). Timeouts are retried too, so the worst-case wait is much longer than the timeout (*source*: `client.ts` doc comment).

**Recommended shape** (inferred from the facts above, not a Knock recommendation): one server module, and actions never let Knock failures escape.

```ts
// app/lib/notifications.server.ts
import Knock from "@knocklabs/node";

const knock = process.env.KNOCK_API_KEY
  ? new Knock({ apiKey: process.env.KNOCK_API_KEY, timeout: 3_000, maxRetries: 1 })
  : null; // no key (tests/offline): notifications become a no-op

export async function notify(
  workflow: string,
  recipients: { id: number; name: string; avatarUrl?: string | null }[],
  data: Record<string, unknown>,
  opts: { idempotencyKey?: string; actorId?: number } = {},
) {
  if (!knock) return;
  try {
    await knock.workflows.trigger(
      workflow,
      {
        recipients: recipients.map((u) => ({ id: String(u.id), name: u.name, avatar: u.avatarUrl ?? undefined })),
        actor: opts.actorId != null ? String(opts.actorId) : undefined,
        data,
      },
      { idempotencyKey: opts.idempotencyKey },
    );
  } catch (err) {
    console.error(`[knock] trigger ${workflow} failed`, err); // never rethrow
  }
}
```

In an action, either `await notify(...)` (bounded to about 6 s worst case with the settings above) or call it without awaiting, after the DB write. Firing without awaiting is safe in a long-lived Node server because `notify` never rejects.

## 2. In-app feed and badge (`@knocklabs/react`)

**Setup** ([React feed guide](https://docs.knock.app/in-app-ui/react/feed)):

```tsx
import { KnockProvider, KnockFeedProvider, NotificationIconButton, NotificationFeedPopover } from "@knocklabs/react";
import "@knocklabs/react/dist/index.css";

<KnockProvider apiKey={publicKey} user={{ id: String(currentUser.id) }} userToken={knockToken}>
  <KnockFeedProvider feedId={feedChannelId}>
    <NotificationIconButton ref={btnRef} onClick={() => setOpen(!open)} />
    <NotificationFeedPopover buttonRef={btnRef} isVisible={open} onClose={() => setOpen(false)} />
  </KnockFeedProvider>
</KnockProvider>
```

**`KnockProvider` props** (*source*: [`react-core/src/modules/core/context/KnockProvider.tsx`](https://github.com/knocklabs/javascript/blob/main/packages/react-core/src/modules/core/context/KnockProvider.tsx)):
- `apiKey`
- `user` (`{ id, ...props }`). The `userId` prop is deprecated.
- `userToken`
- `onUserTokenExpiring`
- `timeBeforeExpirationInMs` (default 30 000 ms, *source*: `client/src/knock.ts`)
- `host`, `logLevel`, `branch`, `i18n`
- `identificationStrategy` (`"inline"` by default, or `"skip"`)
- `enabled` (default `true`). When `false`, the provider renders its children but makes "no identify call, no API requests, and no websocket".

**`KnockFeedProvider` props:** `feedId` (the in-app channel UUID), `colorMode` (`"light"` or `"dark"`), and `defaultFeedOptions` (*source*: [`KnockFeedProvider.tsx`](https://github.com/knocklabs/javascript/blob/main/packages/react-core/src/modules/feed/context/KnockFeedProvider.tsx)). The feed guide's security note says to pass `userToken` to `KnockFeedProvider` ([feed guide](https://docs.knock.app/in-app-ui/react/feed)), but in 0.17.1 that prop exists only on `KnockProvider`. Follow the code.

**Components and hooks exported** by 0.15.1 (*source*: `dist/types/index.d.ts` in the published tarball):
- Components: `NotificationIconButton`, `NotificationFeedPopover`, `NotificationFeed`, `NotificationFeedContainer`, `NotificationCell`, `UnseenBadge`, `MarkAsRead`, `EmptyFeed`
- Hooks: `useKnockFeed`, `useNotifications`, `useNotificationStore`, `useCreateNotificationStore`, `useFeedSettings`, `useKnockClient`, `useAuthenticatedKnockClient`, `useKnockAuthState`, `usePreferences`
- Also: `formatBadgeCount`, `BadgeCountType`

**Unseen vs unread.** Knock tracks `seen_at` and `read_at` separately. "`unseen_count` usually drives badge counts, while `unread_count` indicates items the user hasn't explicitly engaged with." The prebuilt components call `feedClient.markAllAsSeen()` when the feed opens. Headless UIs must do this themselves, or the badge never clears ([Headless feed](https://docs.knock.app/in-app-ui/react/headless/feed)). `NotificationIconButton` takes `badgeCountType="unread"` to count unread instead ([feed guide](https://docs.knock.app/in-app-ui/react/feed)). The feed metadata includes `total_count`, `unread_count`, and `unseen_count` ([In-app API overview](https://docs.knock.app/in-app-ui/api-overview)).

**Marking state.** The feed client has these methods, and each updates the store optimistically ([Feed client ref](https://docs.knock.app/in-app-ui/javascript/sdk/feed-client)):
- `markAsSeen` / `markAsUnseen`
- `markAsRead` / `markAsUnread`
- `markAsArchived` / `markAsUnarchived`
- `markAsInteracted(items, metadata)`
- `markAllAsSeen`, `markAllAsRead`, `markAllAsArchived`. These run server-side and are deferred.
- `markAllReadAsArchived`, which the 0.23.1 source also has.

**Real-time.** "Knock's managed real-time service ... uses a websocket" ([Feeds overview](https://docs.knock.app/in-app-ui/feeds/overview)). The client depends on `phoenix@1.8.9` and connects through a signed gateway URL (*source*: [`client/package.json`](https://github.com/knocklabs/javascript/blob/main/packages/client/package.json), `client/src/api.ts`). The socket event carries badge metadata only, and "might be throttled" ([API overview](https://docs.knock.app/in-app-ui/api-overview)). I found no documented polling fallback. Two options are useful here. `auto_manage_socket_connection` disconnects the socket in hidden tabs. `__experimentalCrossBrowserUpdates` syncs tabs through BroadcastChannel ([feed guide](https://docs.knock.app/in-app-ui/react/feed)).

**SSR safety.** No Knock doc page covers SSR, Remix, or React Router. The [feed](https://docs.knock.app/in-app-ui/react/feed) and [headless](https://docs.knock.app/in-app-ui/react/headless/feed) pages say nothing about it. From the source:
- The ESM entry starts with `"use client"`. That only matters for RSC bundlers. React Router framework mode without RSC ignores it.
- `window`, `document`, and `WebSocket` accesses are guarded with `typeof` checks, so importing the package on the server doesn't crash (`client/src/api.ts`, `pageVisibility.ts`).
- **However,** `useAuthenticatedKnockClient` builds `new Knock(...)` and calls `authenticate()` inside `useMemo`, which runs during the server render. With the default `identificationStrategy: "inline"` and a `user` object, that fires `user.identify()` over HTTP **from the Node server on every SSR request**. Errors are swallowed. If `onUserTokenExpiring` is passed, it also schedules an expiry timer on the server. `useNotifications` initialises the feed in a `useState` initializer, also during render (`react-core/src/modules/core/hooks/useAuthenticatedKnockClient.ts`, `feed/hooks/useNotifications.ts`).
- **Mitigation:** `const hydrated = useHydrated()`, a `useEffect` that sets a flag, and then `<KnockProvider enabled={hydrated} ...>`. The server and first client render both see an idle client with an empty store, so the markup should match. This is inferred and not verified by running it.

**Peer deps** (`@knocklabs/react` 0.15.1): `react` and `react-dom` `^17 || ^18 || ^19`, so React 19.2 is in range. `next` and `@tanstack/react-router` are optional peers. Dependencies include Radix and Knock's `@telegraph/*` design system ([package.json](https://github.com/knocklabs/javascript/blob/main/packages/react/package.json)).

**Styling.** You either import `dist/index.css` and override the `--rnf-*` CSS variables, or drop it and restyle the `rnf-*` classes. `colorMode="dark"` switches to dark mode ([feed guide](https://docs.knock.app/in-app-ui/react/feed)). There is no Tailwind-specific guidance. To match our Tailwind look, the realistic options are mapping our tokens onto `--rnf-*` variables, or building a headless UI with `useNotificationStore` and `feedClient` and our own components.

## 3. User identification, IDs, and enhanced security

**Identify.** v1 uses `client.users.update(userId: string, body)`, which is `PUT /v1/users/{id}`. It "create[s] or update[s]" and merges properties (*source*: [`users.ts`](https://github.com/knocklabs/knock-node/blob/main/src/resources/users/users.ts)). There is also bulk `POST /v1/users/bulk/identify`. Knock recommends "using your internal user identifier for the `id` value", and `id` is the only required property ([Identifying recipients](https://docs.knock.app/managing-recipients/identifying-recipients)). The docs give no format or charset rules, but every SDK signature types the ID as `string`. So use `String(user.id)` consistently on the server and client. In this app, inline identify in each trigger, plus client inline identify, covers us without a separate sync job.

**Enhanced security mode** ([Security & authentication](https://docs.knock.app/in-app-ui/security-and-authentication)):
- It's off by default. Without it, "a public key request can act as any user". Knock says to enable it before release, and it's set per environment.
- The JWT is signed **RS256** with the environment's signing key (Platform > API keys, shown once, base64-PEM or PEM). `sub` is the user ID. `iat` and `exp` are recommended. `grants` and `explicit_grants` are optional.
- On the client, pass `userToken` to `KnockProvider`. Use `onUserTokenExpiring` to fetch a new token. The callback has the signature `(currentToken, decoded) => Promise<string | void>` (*source*: `client/src/interfaces.ts`). The docs suggest matching token expiry to session expiry where possible.

```ts
import { signUserToken } from "@knocklabs/node"; // reads KNOCK_SIGNING_KEY by default
const knockToken = await signUserToken(String(currentUser.id), { expiresInSeconds: 3600 }); // default 3600
```

*Source*: [`src/lib/tokenSigner.ts`](https://github.com/knocklabs/knock-node/blob/main/src/lib/tokenSigner.ts) (`alg: 'RS256'`, default `60 * 60`). The docs' Express example imports from `@knocklabs/node/lib/tokenSigner`. In v1 it's also a root export.

For Cadence, sign the token in the `layout.app.tsx` loader and return it alongside `currentUser`, together with the public key and feed channel ID. Client code can't read `process.env`, unlike the docs example. For refresh, a resource route such as `/api/knock-token` can sign a fresh token from the session. Switching users in the DevUI changes `user.id`, and the client re-authenticates and remounts the feed, because `feedProviderKey` includes `userId` (*source*: `useAuthenticatedKnockClient.ts`, `KnockFeedProvider.tsx`).

**Keys.**
- The secret key is for the backend only.
- The public key is for the browser. It can read and update the current user, their preferences, channel data, and feeds.
- The signing key is backend only ([Security](https://docs.knock.app/in-app-ui/security-and-authentication)).

**Environments.** Production always exists. Enabling environments adds Development. Each environment has its own public and secret keys, and users, messages, logs, and tenants are "never shared between environments". A new development environment starts with no users. Workflows are committed in Development and promoted to Production ([Environments](https://docs.knock.app/concepts/environments)).

## 4. Preferences

**Structure.** A `PreferenceSet` is built from `categories`, `channel_types`, `channels` (keyed by channel UUID), `workflows`, and `commercial_subscribed` on the default set. Each value is a boolean or an object with `channel_types` or `conditions` (`{ variable, operator, argument }`) ([Preferences overview](https://docs.knock.app/preferences/overview), [API: set preferences](https://docs.knock.app/api-reference/users/set_preferences)). `in_app_feed` is a typed `channel_types` key (*source*: [`src/resources/recipients/preferences.ts`](https://github.com/knocklabs/knock-node/blob/main/src/resources/recipients/preferences.ts)).

**Evaluation** ([overview](https://docs.knock.app/preferences/overview)):
- The **environment default set** has the lowest priority. You set it in the dashboard or via the Management API.
- Then the **tenant default**, which is an advanced feature.
- Then the user's own set, `default` or tenant-specific.
- Channel beats channel type. A `false` category blocks the notification.
- Anything unset counts as `true`, and a notification is sent only if every applicable preference is `true`.
- **Workflow override:** "Manage workflow > Override recipient preferences" makes a workflow ignore recipient preferences. That suits mandatory notices, such as Team Admin seat or billing events.

**Per-workflow in-app opt-out.** Yes:

```ts
await knock.users.setPreferences(String(userId), "default", {
  __persistence_strategy__: "merge", // default is destructive replace
  workflows: { "lesson-published": { channel_types: { in_app_feed: false } } },
});
```

*Source*: `users.ts` doc comment ("By default, this is a destructive operation ... Use `__persistence_strategy__: 'merge'`"). `getPreferences(userId, "default")` reads a set.

On the client, `knock.user.getPreferences()` and `setPreferences()` work with the public key or user token, and `usePreferences({ preferenceSet, tenant })` wraps them with SWR (*source*: [`react-core/src/modules/preferences/hooks/usePreferences.ts`](https://github.com/knocklabs/javascript/blob/main/packages/react-core/src/modules/preferences/hooks/usePreferences.ts)).

**Prebuilt UI.** There is no preferences component in `@knocklabs/react` 0.15.1. The type exports contain only `usePreferences` (*source*: `dist/types/index.d.ts`). The [React preferences guide](https://docs.knock.app/in-app-ui/react/preferences) shows a `PreferenceCenter` you write yourself. Its checkboxes are disabled for channel types missing from the set. So seed an **environment default set** that lists every workflow or category with `in_app_feed: true`, or the UI has nothing to render. The overview also mentions a hosted preference center, which I didn't evaluate.

**Mapping to Cadence roles.** Categories, such as `course-updates`, `team-admin`, and `platform`, give one toggle per group of workflows. Role gating itself (who *receives* what) belongs in our trigger code, not in preferences.

## 5. Free tier and pricing

From [knock.app/pricing](https://knock.app/pricing):
- **Free:** **10,000 messages/month**, unlimited environments, unlimited team members and stored profiles, preferences, built-in multi-tenancy, version control, Google SSO, 30-day log retention, and unlimited, configurable feed retention.
- **Enterprise-only:** per-tenant preferences and branding, SAML, audit logs, and custom roles.
- **Starter:** $250/month for 50,000 messages, then $0.005 per message.

**What a message is.** "A single message delivered to a single user on a single channel." In-app counts, and in-app plus email equals 2. Workflow triggers aren't billed. Failed or bounced messages aren't billed. Guide views aren't counted ([pricing](https://knock.app/pricing)). So notifying a 30-student cohort of a new lesson costs 30 messages.

The [plans page](https://docs.knock.app/manage-your-account/knock-plans) adds three points:
- Usage "can accrue in any environment", so development counts.
- **The in-app channel doesn't support sandbox mode.** Channel conditions can limit in-app message creation in non-production environments.
- I could not confirm whether the Free plan hard-stops or bills overage.

**Enhanced security** isn't listed as a gated feature on either page, so I couldn't confirm any plan gating for it.

## 6. Sanity check: Novu and MagicBell

**Novu**
- The free plan has 10,000 workflow runs/month, **at most 5 workflows**, 2 environments, and 24 h activity retention. Pro costs $30/month. Self-hosting is Enterprise-only ([novu.co/pricing](https://novu.co/pricing)).
- The `@novu/react` Inbox **includes a Preferences component**. It requires React 18 or later, and React 19 is supported. Updating an existing subscriber needs an HMAC `subscriberHash` ([Inbox overview](https://docs.novu.co/platform/inbox/overview)).
- The only framework quickstart is Next.js, which uses `'use client'`. There is no React Router or SSR guidance ([Next.js quickstart](https://docs.novu.co/platform/quickstart/nextjs)).
- Verdict: the prebuilt preferences UI is the only real advantage, and the 5-workflow cap would pinch. Nothing here disqualifies Knock.

**MagicBell**
- The free Builder plan has **1,000 deliveries/month**. Startup costs $249/month for 50,000. Deliveries are counted per channel ([magicbell.com/pricing](https://www.magicbell.com/pricing)).
- `@magicbell/react` has a Provider that takes a server-generated User JWT, an `Inbox`, and a **prebuilt `UserPreferences`** component. The page gives no SSR notes or React version information ([MagicBell React docs](https://www.magicbell.com/docs/libraries/magicbell-react)).
- Verdict: the free tier is 10x smaller than Knock's, and SSR is undocumented there too. Nothing makes Knock the wrong choice.

## 7. Risks and surprises for this stack

1. **SSR side effects** (*source*, inferred). `KnockProvider` authenticates and runs inline `identify` during the server render. That adds one outbound HTTP call per page view from Node, plus a possible leaked token-expiry timer. Fix with `enabled={hydrated}`, or `identificationStrategy="skip"` plus server-side identify. Not verified by running it.
2. **Default timeout of 60 s with 2 retries.** An un-tuned `trigger` inside an action can hang a form submission for minutes. Set `timeout` and `maxRetries`, and always catch ([README](https://github.com/knocklabs/knock-node)).
3. **Integer IDs.** Knock IDs are strings, so stringify everywhere. A subtler problem: every developer's local SQLite seed reuses IDs `1..n`. If several developers share one Knock **Development** environment, user `"1"` is the same Knock user for all of them, and feeds and preferences bleed across. Options are one Knock account per developer (environments are unlimited on Free) or a prefix such as `dev-<name>-1`. The SDKs also accept a `branch` option, but I didn't research what branches isolate.
4. **No mock or test mode for in-app.** I found no official mock server or offline mode. Sandbox mode doesn't apply to in-app ([plans](https://docs.knock.app/manage-your-account/knock-plans), [Testing workflows](https://docs.knock.app/send-notifications/testing-workflows)). For tests, wrap Knock behind our own `notify()` module and inject a fake, or pass the SDK's `fetch` / `baseURL` options to a stub. Run with no `KNOCK_API_KEY`, which makes `notify` a no-op, and with `enabled={false}` on the client when there is no public key.
5. **Local dev without network.** The feed simply stays empty, because client errors are swallowed and inline identify only logs. Triggers fail fast once the timeout is low.
6. **Dev usage is billable.** Seeding and manual testing in Development burn the 10k/month. Each recipient times each in-app step is one message.
7. **Seeding the dev environment.** It starts with no users. Inline identify on trigger plus client inline identify creates users lazily. Bulk identify exists if we want to seed the DevUI user list up front ([Identifying recipients](https://docs.knock.app/managing-recipients/identifying-recipients)).
8. **Cost of identify calls.** Identify calls aren't billed messages, and the docs give no per-call cost. They do count against rate limits, which are per environment, or per environment plus user with a token.
9. **Preferences UI is ours to build.** This includes seeding an environment default set so the toggles render.
10. **Styling.** The prebuilt popover brings its own CSS and Radix and Telegraph dependencies. Expect to override `--rnf-*` variables or go headless to match the Tailwind UI.
11. **Docs drift.** The feed guide puts `userToken` on `KnockFeedProvider`, while the code has it on `KnockProvider`. Older snippets use `users.identify`. Pin versions and trust the type definitions.
